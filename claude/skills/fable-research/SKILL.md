# Fable Deep Research

コードベースを自分の目で読み込み、実装前に research.md へ調査結果を整理するスキル。
このスキルの目的は「速く答えを出すこと」ではなく「**間違った前提で実装に入らないこと**」。

調査中はコードを変更しない。書き込むのは research.md のみ。

## 絶対原則

1. **grep のヒットは証拠ではなくポインタ。** ヒット行だけで判断せず、必ずその関数・ファイル全体を開いて読む。
2. **名前から挙動を推測しない。** `validateUser` が何を validate するかは実装を読むまで不明として扱う。
3. **事実と推測を分離する。** research.md 上で「事実（file:line 付き）」と「推測」を明確に分ける。file:line を付けられない主張は事実として書かない。
4. **最初のもっともらしい答えで止まらない。** 結論が出たら、必ず「この結論を壊す証拠」を探すパス（反証フェーズ）を実行してから確定する。これはスキップ不可。
5. **未解決の疑問リストを常に持つ。** 調査中に浮かんだ疑問は必ずリスト化し、コードを読んで解消するか、「何が分かれば解決するか」付きで未解決として明記する。黙って消さない。

## 手順

### Phase 0: 完了条件の定義

調査を始める前に「何が分かれば調査完了か」を2〜5個の具体的な質問として書き出す。
例:「この API の呼び出し元は全部でいくつか」「このカラムに書き込む経路は何本あるか」。
以降のフェーズはこの質問に答えるために行う。質問と無関係な深掘りはしない。

### Phase 1: 地図作り（広く浅く）

- ディレクトリ構成、README / AGENTS.md / ADR、package.json（monorepo なら各 workspace）を確認
- 構造を決めるファイルを特定して読む: ルーティング定義、DB スキーマ、エントリポイント、DI/初期化コード
- 独立した検索・読み込みは**まとめて並列実行**する。広い横断検索は Explore サブエージェントに委任してよい

### Phase 2: 経路追跡（狭く深く）

対象機能の end-to-end データフローを追う。
UI → route → handler → service → DB / 外部 API → レスポンス、のように**各ホップを実際に開いて読む**。
1ホップでも「たぶんこうなっている」で飛ばしたら、その先の理解はすべて推測になる。

追いながらテキストでフロー図を書く（research.md に載せる）。

### Phase 3: 影響範囲の全数調査

変更対象のシンボルについて「呼び出し元を全部見つけた」と言えるまで検索する。1回の grep で満足しない:

- シンボル名の直接参照（`grep -rn`）
- re-export・別名・ラッパー経由の間接参照
- 文字列としての参照（ルートパス、イベント名、設定キー、環境変数）
- コード以外: マイグレーション、cron / バックグラウンドジョブ、CI 設定、テスト、シードデータ

見つけた呼び出し元は一覧化し、それぞれ「変更の影響を受けるか」を判定する。

### Phase 4: 歴史と意図

不自然なコード・冗長に見えるコードは、消す前提で考えずに `git log -L` / `git blame` / 関連 PR を確認する。
ワークアラウンドや暗黙の制約はコメントではなく履歴に埋まっていることが多い。

### Phase 5: 反証（スキップ不可）

Phase 0 の質問への答え＝結論を1つずつ取り上げ、「これが間違いだとしたら、どんな証拠があるはずか」を考えて実際に探す:

- 別の書き込み/読み取り経路はないか
- feature flag・環境変数・設定による分岐で挙動が変わらないか
- 例外ハンドラやフォールバックが想定と違う経路を作っていないか
- テストコードが自分の理解と矛盾する挙動を検証していないか

反証が見つかったら結論を修正し、該当フェーズからやり直す。

### 完了条件チェック

以下を満たしたら research.md を書いて終了:

- [ ] Phase 0 の質問すべてに答えた（または未解決として明記した）
- [ ] end-to-end のデータフローを何も見ずに説明できる
- [ ] すべての「事実」に file:line が付いている
- [ ] 反証フェーズを実行した

## 出力: research.md

出力先はタスクのディレクトリ（例: `.local/issues/<番号>/research.md`）。番号がなければタスク名のディレクトリを使う。

```markdown
# 調査: <テーマ>

## 質問と結論
（Phase 0 の質問それぞれに1〜3行で回答）

## 事実
（すべて file:line 付き。読んで確認したことだけ）

## データフロー
（テキスト図。各ホップに file:line）

## 影響範囲
（呼び出し元・参照の全数一覧と、影響の有無）

## 前提・制約・落とし穴
（履歴から分かった意図、暗黙の制約、ワークアラウンド）

## 推測（未確認）
（事実と区別して明記）

## 未解決の疑問
（それぞれ「何が分かれば解決するか」を添える）
```

## アンチパターン（やりがちな失敗）

- grep 1発のヒットだけ見て結論を出す
- ファイル名・関数名からの推測をそのまま事実として書く
- 呼び出し元を1つ見つけて「影響範囲を確認した」と言う
- 調査依頼と無関係なリファクタ提案を混ぜる
- 長いコード引用ばかりで主張（で、何が分かったのか）がない
- 都合の悪い未解決疑問を書かずに終える
