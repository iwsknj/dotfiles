# Fable Plan

調査結果に基づいて実装計画を plan.md に作成するスキル。
このスキルの目的は「網羅的な文書を書くこと」ではなく「**実装がそのまま通る、最小で正しい計画を作ること**」。

計画中はコードを変更しない。書き込むのは plan.md のみ。

## 前提

- **調査が先。** タスクディレクトリ（例: `.local/issues/<番号>/`）に research.md があれば必ず読む。なければ先に fable-research を実行する。
- 設計中に research.md にない前提が必要になったら、推測で埋めずに**調査に戻る**（該当箇所のコードを読んで確認してから続ける）。

## 設計原則

1. **最小の diff で問題を完全に解決する。** YAGNI / KISS / DRY。shim・フォールバック・後方互換のための調整コードは入れない。「念のため」の抽象化・オプション・設定は追加しない。
2. **既存パターンに従う。** このコードベースで最も近い既存実装（アナログ）を1つ特定し、その構造・命名・エラーハンドリングを踏襲する。新しい流儀を持ち込まない。
3. **データモデルを先に決める。** スキーマ・型・API 契約が正しければ挙動は素直に書ける。逆は成り立たない。
4. **すべての設計判断は調査で確認した事実にトレースできること。** 「一般的にはこうする」ではなく「このコードベースがこうなっているから、こうする」。
5. **代替案は2〜3個だけ簡潔に比較して1つ選ぶ。** 選定理由を1〜3行で書く。延々と比較しない。決められない場合は、判断に必要な事実が調査で欠けているサイン。

## 手順

### Step 1: 受け入れ条件

要件を「観測可能な振る舞い」として2〜5個書き出す。
例:「×: ログインを改善する」「○: 未認証で /x-accounts にアクセスすると /login にリダイレクトされる」。
以降のすべての設計はこの受け入れ条件を満たすためだけに行う。

### Step 2: 既存アナログの特定

似たことをしている既存実装を1つ選び、file:line で示す。踏襲する点と、今回意図的に変える点を明記する。

### Step 3: データモデル・契約の設計

DB スキーマ、型、API のリクエスト/レスポンス、関数シグネチャを先に確定する。
マイグレーションが要る場合は、このプロジェクトのマイグレーション運用（生成方法・適用タイミング）を research.md / AGENTS.md で確認して従う。

### Step 4: 変更ファイルの全列挙

変更・追加・削除するファイルを全部列挙し、各ファイルに1行で「何をするか」を書く。
research.md の影響範囲一覧と突き合わせ、呼び出し元の修正・テスト・マイグレーション・ジョブに漏れがないか確認する。

### Step 5: コードスニペット

主要な変更はスニペットで示す。**書く前に対象ファイルの該当箇所を必ず開く**こと:

- import・関数名・型は実在するものだけを使う。API を発明しない
- 既存コードを修正するスニペットは、実際の現行コードを引用した上で変更後を示す
- 周辺コードのスタイル（命名、エラーハンドリング、コメント密度）に合わせる

### Step 6: エッジケースと故障モード

該当するものだけ検討して計画に反映する（該当しない項目を無理に埋めない）:

- 空・null・0件・重複
- 並行実行・二重送信・冪等性
- 部分失敗（外部 API 失敗時に DB だけ更新される等）
- 認可境界（他人のリソースに触れないか）
- マイグレーションとデプロイの順序（旧コード + 新スキーマの瞬間に壊れないか）

### Step 7: 実装順序

各ステップ完了時点でビルド・テストが通る順序に並べる。「全部書いてから最後に動かす」計画にしない。

### Step 8: 検証計画

「テストを書く」で済ませない。具体的に書く:

- 実行するコマンド（テスト、typecheck、lint）
- 手動確認の手順（起動方法、叩く URL、期待する表示・レスポンス）
- 受け入れ条件（Step 1）それぞれをどの検証でカバーするか

### Step 9: セルフレビュー（スキップ不可）

完成した計画を敵対的に読み直す。1項目ずつ明示的に確認する:

- [ ] この計画を実装すると壊れるものはないか（research.md の影響範囲一覧と再照合）
- [ ] research.md の事実と矛盾する記述はないか
- [ ] スニペット内の関数名・型・import はすべて実在するか（怪しければ開いて確認）
- [ ] 受け入れ条件のうち、この計画で満たされないものはないか
- [ ] 削れる要素はないか（この変更、本当に今回必要か？を各変更に問う）

問題が見つかったら該当 Step に戻って修正してから確定する。

## 出力: plan.md

出力先は research.md と同じタスクディレクトリ。

```markdown
# 実装計画: <機能名>

## 受け入れ条件
（観測可能な振る舞いのリスト）

## アプローチ
（全体像。踏襲する既存アナログを file:line で明記。検討した代替案と選定理由を簡潔に）

## データモデル・契約
（スキーマ / 型 / API の変更）

## 変更ファイル一覧
（ファイルごとに1行の説明）

## 実装詳細
（変更ごとにスニペット。現行コード → 変更後）

## エッジケース・故障モード
（該当するものだけ）

## 実装順序
（各ステップでビルドが通る順）

## 検証計画
（コマンド + 手動確認手順。受け入れ条件との対応）
```

## アンチパターン（やりがちな失敗）

- 調査せずに一般論・ベストプラクティスだけで設計する
- 存在しない API・ヘルパー・型をスニペットに書く
- 「将来のために」の抽象化・設定・オプションを足す
- 変更ファイル一覧からテスト・マイグレーション・ジョブが漏れる
- 検証計画が「テストを書く」の1行で終わる
- 受け入れ条件に関係ない改善（ついでのリファクタ）を計画に混ぜる
